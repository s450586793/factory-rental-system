# 合同双方信息设计

## 目标

新增和编辑合同时，分别记录甲乙双方的名称、营业执照号码、联系人和电话，并在自动生成的租赁合同及安全协议中使用对应信息。甲方可按个人或公司名义签约，历史合同重新下载时内容保持稳定。

## 数据模型

在每份合同上新增以下甲方快照字段：

- `lessorName`：甲方名称
- `lessorLicenseCode`：甲方营业执照号码
- `lessorContactName`：甲方联系人
- `lessorPhone`：甲方电话

乙方继续使用现有字段：

- `tenantName`：乙方名称
- `licenseCode`：乙方营业执照号码
- `contactName`：乙方联系人
- `tenantPhone`：乙方电话

所有双方信息字段均允许为空，不在前端或后端设置必填校验。字段仍保留合理的长度限制，避免异常超长内容影响页面和 PDF 排版。

## 默认值与继承

已有房源新增合同时，优先从该房源开始日期最新的一份合同继承甲方四项信息，同时保留现有的乙方、日期、租金和押金继承逻辑。

房源没有历史合同时：

- 甲方名称为空；
- 甲方营业执照号码为空；
- 甲方联系人默认为“吴孝斌”；
- 甲方电话默认为 `18651510352`。

新建厂房时顺带录入首份合同，也使用上述无历史合同默认值。

## 历史数据迁移

历史合同此前固定以“吴孝斌”为甲方。迁移时为已有合同写入：

- 甲方名称：“吴孝斌”；
- 甲方营业执照号码：空；
- 甲方联系人：“吴孝斌”；
- 甲方电话：`18651510352`。

这样历史合同重新生成时与原有签约主体一致，同时具备新的联系人信息。

## 表单与列表

“新建厂房时录合同”和“已有房源新增/编辑合同”两处表单都分为甲方信息和乙方信息，每方包含名称、营业执照号码、联系人、电话四项。

现有营业执照文件上传仍属于乙方资料，本次不增加甲方营业执照文件上传。合同列表保持当前信息密度，不新增四个甲方列；甲方信息可在编辑合同中查看和修改。

## PDF 映射

自动生成 PDF 时按以下规则写入：

- 租赁合同首页分别显示甲乙双方名称、营业执照号码、联系人和电话；
- 租赁合同签字盖章区分别显示甲乙双方名称；
- 安全协议甲乙方单位位置分别显示双方名称；
- 安全协议联系人位置分别显示双方联系人；联系人为空时回退到对应方名称；
- 不再使用写死的甲方名称或联系人常量。

空字段以“未填写”展示，避免 PDF 中出现空白标签或 `undefined`。

## 接口与错误处理

合同创建和更新接口接收甲方四项字段，对所有双方文本字段统一去除首尾空格。缺失的可选字段保存为空字符串。接口响应和前端类型同步返回甲方四项字段。

字段长度超限时沿用现有 DTO 校验错误处理，不向用户暴露内部数据库或文件路径信息。

## 测试与验收

- 数据迁移测试：新列存在，历史合同正确回填，回滚可移除新列。
- 服务测试：创建和更新时保存、清理甲方四项字段。
- PDF 测试：个人甲方、公司甲方、空字段及联系人回退均映射正确，旧的写死常量不再影响输出。
- 前端测试：无历史合同默认联系人和电话；有历史合同继承甲方信息；编辑合同回填；保存请求包含双方信息；双方字段为空时仍可保存。
- 完整运行后端测试、前端测试、lint 和 build，并验证数据库迁移。
- 推送后等待 GitHub Actions 镜像构建成功，再更新 DSM 项目并核对线上版本和合同生成接口。
